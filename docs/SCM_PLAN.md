## Part 1: OSS Branching-Policy Summary (Kubernetes)

Kubernetes keeps one long-lived development branch and cuts a separate `release-1.X` branch for each supported minor version. Its root `CONTRIBUTING.md` is only a few lines: it requires contributors to sign the Contributor License Agreement and sends them to the Contributor's Guide in the community repository, where the real process lives.

**Branching.** New work lands on the default branch through pull requests. Fixes needed on a supported release are backported as cherry-pick PRs against `release-1.X`, usually generated by a helper script on an `automated-cherry-pick-of-*` branch. Maintainers accept security and regression fixes into the stable branch, but not new features once a version is beta or GA (cherry-pick guidelines).

**Merge and review requirements.**

* Each directory has an `OWNERS` file naming its reviewers and approvers. A reviewer comments `/lgtm`; an approver comments `/approve`. The bot adds the `approved` label only once every required `OWNERS` file has approval.
* Merging is done by the CI bot, not by a person clicking merge, and only after required automated tests pass. Some repositories also label PRs so they are squash-merged.
* Cherry-picks carry one extra gate: Patch Release Team members must apply the `cherry-pick-approved` label, and the PR needs a release note (patch release handbook).

**Lesson for fastapp.** The core ideas transfer to a small team: short-lived PRs into one default branch, a named human approval, and automated checks before merge. Long-lived release branches exist because Kubernetes supports several versions at once, which a one-person app does not need.

## Part 2: SCM Plan for fastapp

### 1. Purpose

This plan sets how fastapp, a small React web app built with Vite, is changed, checked and released. Its goals are that `main` always builds, every change has a recorded reason, and any mistake can be undone. It is written so a new contributor can open a correct first pull request by following sections 4 and 5.

### 2. Scope

* **In scope:** source code in `src/` and `public/`, configuration (`package.json`, `package-lock.json`, `vite.config.js`, `.oxlintrc.json`), documentation (`README.md`, this plan) and CI workflow files in `.github/`.
* **Out of scope:** `node_modules` and build output (both excluded by `.gitignore`), secrets and `.env` files (never committed) and the hosting dashboard.
* **People:** the maintainer, one reviewer and any contributor who joins later.

### 3. Roles and Responsibilities

| Role | Holder | Responsibilities |
| --- | --- | --- |
| Maintainer, author and release manager | Sanaipei | Owns the repository settings, writes changes, tags releases, triages issues |
| Contributor | Anyone who joins later | Works on a branch, opens a PR linked to an issue and answers review comments within two working days |
| Reviewer | Second team member (@thuomwangi) | Approves every PR before merge; one approval is required, and CODEOWNERS assigns the reviewer |

The repository has two members: the maintainer and one reviewer. GitHub does not let anyone approve their own pull request, so every PR needs the reviewer's approval.

### 4. Version Control Strategy

**Choice: GitHub Flow.** One protected branch, `main`, is always working. All changes are made on short-lived branches and merged back through pull requests.

**Why it fits fastapp:**

* **Team size (2):** Git Flow's permanent `develop`, `release` and `hotfix` branches exist to coordinate several people and several live versions. For two people they are extra merges with no benefit.
* **Release cadence:** fastapp is a front-end app with a single live version, released whenever a feature set is finished. There is nothing to maintain in parallel, so no release branches are needed.
* **Risk tolerance:** low to moderate. It is a front-end app with a student form and no payments, so the main risk is shipping a broken build. Required CI on every PR covers that.
* **Why not trunk-based:** committing straight to `main` skips the branch and PR record that shows how each change was reviewed and tested. Short-lived branches cost a few seconds and keep that history.

**Branch convention.** Names follow `type/issue-number-short-description`, in lowercase with hyphens.

| Branch | Purpose | Lifetime |
| --- | --- | --- |
| `main` | Working code, changed only through merged PRs | Permanent |
| `feature/3-student-form-validation` | New functionality | Merge within 3 days |
| `fix/7-form-submit-error` | Bug fixes | Merge within 2 days |
| `docs/1-add-scm-plan` | Documentation | Merge within 2 days |
| `chore/9-update-dependencies` | Tooling and dependency updates | Merge within 2 days |

**Rules for `main`** (set in GitHub branch protection): no direct pushes, no force pushes, a pull request with one approval is required, the CI check must pass and the branch must be up to date, commits must be signed, and squash merge is the only merge method so history stays linear. Branches are deleted after merge. Commits are signed with an SSH key registered on GitHub as a signing key, so they show as Verified.

Commits use short imperative messages in the Conventional Commits style, for example `feat: add name validation` or `fix: stop double submit`.

### 5. Change Control Strategy

Every change to `main` follows these steps, in this order:

1. **Start from an issue.** Create or pick a GitHub issue that says what and why.
2. **Branch from an up-to-date `main`:** `git checkout main`, `git pull`, then `git checkout -b feature/3-short-name`.
3. **Commit small.** One issue per branch, with clear commit messages.
4. **Push and open a pull request** using the PR template: what changed, `Closes #<issue>` and how it was tested.
5. **Wait for CI.** Lint and build must both pass.
6. **Review the diff on GitHub** and tick the checklist: no debug code, no secrets, and the change tried in the browser with `npm run dev`. The reviewer must approve before merge.
7. **Squash and merge,** then delete the branch.

**Change types**

| Type | Process |
| --- | --- |
| Normal change | Steps 1 to 7 |
| Urgent fix | Same steps on a `fix/` branch, merged the same day |
| Dependency or config change | Same steps on a `chore/` branch, and the PR states why the change is safe |

Settings may be bypassed only to repair a broken `main`, and the reason is recorded on the related issue. If a merged change breaks `main`, it is reverted first and fixed afterwards.

### 6. CI/CD Process Control Strategy

Checks run on GitHub Actions. The workflow lives in `.github/workflows/ci.yml`, so it is versioned and reviewed like any other code.

| Trigger | What runs | Outcome |
| --- | --- | --- |
| Pull request to `main` | `npm ci`, `npm run lint`, `npm run build` | The check must pass before merge |
| Push to `main` | The same three steps | Confirms `main` still builds after the squash merge |
| Release tag `vX.Y.Z` | Build from the tag, then publish the `dist/` output | Deploys only released versions |

**Controls**

* Hosting is not set up yet. When it is, a deploy workflow will run only on release tags, never on a plain merge.
* `package-lock.json` is committed and CI uses `npm ci`, so every build uses the same dependency versions.
* Secrets live only in GitHub Actions secrets, never in the repository.
* If `main` goes red, no new PRs are merged until it is fixed or the breaking change is reverted.
* Changes to workflow files are described in their PR, since they control what can be merged.

### 7. Issue Tracking Tool and Workflow

**Tool:** GitHub Issues with a GitHub Projects board. It lives next to the code, so issues, branches and PRs link to each other with no extra tool.

* **Labels:** type (`bug`, `feature`, `chore`, `docs`) and priority (`high`, `medium`, `low`).
* **Board columns:** Todo, In progress, In review, Done.
* **Workflow:** every piece of work gets an issue, even when working alone. Bug issues state the steps to reproduce, what was expected and what happened. The maintainer reviews the backlog weekly and sets labels and priority.
* **Linking:** each branch name carries the issue number, and `Closes #<number>` in the PR closes the issue on merge.
* **Milestones:** one per planned release, such as `v0.2.0`, so each release's scope is visible.
* **Definition of done:** merged to `main` with CI green and the change checked in the browser.

### 8. Release Strategy

**Versioning:** Semantic Versioning, `vMAJOR.MINOR.PATCH`. The app stays on `v0.x.y` while it is under development, and `v1.0.0` marks the first complete, usable version. After that, breaking changes bump MAJOR, new features bump MINOR and fixes bump PATCH.

**Cadence:** a release is cut whenever a milestone's issues are done, roughly every two to four weeks. There is no fixed schedule because there is one developer and no users waiting on a date.

**Release steps**

1. Confirm `main` is green and every issue in the milestone is closed.
2. Raise the version in `package.json` through a `chore/` PR and merge it.
3. Create an annotated tag on the merge commit, for example `git tag -a v0.2.0 -m "Student form validation"`, and push it.
4. Publish a GitHub Release with notes taken from the merged PR titles.
5. Once hosting exists, the tag triggers the deploy workflow.

**Hotfixes:** a `fix/` branch from `main`, the normal PR path on the same day, and a new PATCH tag.

**Rollback:** redeploy the previous tag, then revert the faulty PR on `main`.

**Release branches:** none. If fastapp ever has to support several live versions at once, `release/x.y` branches would be added, as Kubernetes does.
